# 기능 명세서: Generate Emotion Card

**기능 브랜치**: `001-generate-emotion-card`  
**작성일**: 2026년 1월 20일  
**상태**: 초안  
**입력**: 사용자 설명: "GitHub 활동 기반의 '시스템 관리자' 페르소나 분석 결과를 SVG 이미지로 반환하는 /card.svg 엔드포인트 구현"

## 명확화

### 세션 2026-01-20
- Q: 분석 엔진 및 LLM 스택은 무엇을 사용합니까? → A: HuggingFace(로컬 감정 분석) + Gemini Flash Lite(LLM 페르소나 생성) 조합을 사용합니다.
- Q: 비동기 분석 작업은 어떻게 처리합니까? → A: **Celery 워커와 Redis 브로커**를 사용하여 웹 요청과 완전히 분리된 백그라운드 프로세스에서 처리합니다.
- Q: 분석 중(Cold Miss) 상태일 때 카드 디자인은 어떻게 처리합니까? → A: "분석 중(Analyzing...)"이라는 정적 안내 문구가 포함된 단순 플레이스홀더 SVG를 제공합니다.
- Q: 데이터베이스 및 인프라 구성은 어떻게 됩니까? → A: 비동기 작업의 안정성과 동시성 제어를 위해 **PostgreSQL**을 사용하며, Redis와 함께 Docker로 구성합니다. 서버는 **ASGI(Daphne/Uvicorn)** 기반으로 구동됩니다.

## 사용자 시나리오 및 테스트 *(필수)*

### 사용자 스토리 1 - 최초 사용자 카드 조회 (Cold Miss) (우선순위: P1)

사용자가 처음으로 자신의 GitHub ID를 사용하여 카드 URL에 접근했을 때, 시스템이 아직 분석되지 않았음을 인지하고 즉시 "분석 중"이라는 시각적 피드백을 제공해야 합니다.

**이 우선순위인 이유**: 사용자가 긴 분석 시간을 기다리지 않고 즉각적인 응답을 받아야 사용자 경험(UX)이 저하되지 않습니다. 이것은 "지연 없는 응답" 전략의 핵심입니다.

**독립적 테스트**: 데이터베이스에 존재하지 않는 새로운 사용자 ID로 요청을 보내 "분석 중" SVG가 반환되는지 확인하고, Celery 워커에서 분석 작업이 시작되었는지 로그 등을 통해 검증할 수 있습니다.

**인수 시나리오**:

1. **주어진 조건** 시스템에 데이터가 없는 새로운 사용자 `newuser`, **조건** `GET /card.svg?username=newuser` 요청, **결과** HTTP 200 OK와 함께 "분석 중(Analyzing System...)" 플레이스홀더 SVG가 즉시 반환됨.
2. **주어진 조건** 위 요청 직후, **조건** 시스템 내부 상태 확인, **결과** `newuser`에 대한 Celery 비동기 작업이 큐에 등록되어야 함.

---

### 사용자 스토리 2 - 분석 완료 후 카드 조회 (Hit & Fresh) (우선순위: P1)

분석이 완료된 후 사용자가 다시 카드를 조회하면, 최근(1시간 이내) 분석된 페르소나 결과가 담긴 카드를 확인할 수 있어야 합니다.

**이 우선순위인 이유**: 기능의 본질적인 목적인 "결과 제공"을 달성하는 시나리오입니다.

**독립적 테스트**: 분석 데이터를 강제로 주입하거나 분석 완료를 기다린 후, 동일한 ID로 요청하여 올바른 결과 SVG가 반환되는지 확인합니다.

**인수 시나리오**:

1. **주어진 조건** `existinguser`에 대한 분석이 30분 전에 완료됨, **조건** `GET /card.svg?username=existinguser` 요청, **결과** 최신 페르소나 분석 결과가 반영된 SVG가 반환됨.
2. **주어진 조건** 위 요청 발생, **조건** 시스템 내부 상태 확인, **결과** 새로운 Celery 작업이 생성되지 않아야 함.

---

### 사용자 스토리 3 - 만료된 데이터 조회 및 백그라운드 갱신 (Hit & Stale) (우선순위: P2)

마지막 분석으로부터 시간이 지난(1시간 이상) 후 사용자가 접근했을 때, 사용자는 기다림 없이 기존 카드를 먼저 보고, 시스템은 보이지 않는 곳에서 최신 상태로 갱신해야 합니다.

**이 우선순위인 이유**: 데이터의 최신성을 유지하면서도 응답 속도를 희생하지 않는 "Stale-While-Revalidate" 전략의 핵심 구현입니다.

**독립적 테스트**: 데이터베이스의 분석 시각을 2시간 전으로 조작한 후 요청을 보내, 즉시 응답이 오는지와 동시에 백그라운드 작업이 시작되는지 확인합니다.

**인수 시나리오**:

1. **주어진 조건** `olduser`에 대한 분석이 2시간 전에 완료됨, **조건** `GET /card.svg?username=olduser` 요청, **결과** 2시간 전의 분석 결과가 담긴 SVG가 **지연 없이** 즉시 반환됨.
2. **주어진 조건** 위 요청 직후, **조건** 시스템 내부 상태 확인, **결과** `olduser`에 대한 새로운 Celery 분석 작업이 시작되어야 함.

---

### 엣지 케이스

- **중복 요청 폭주**: 동일한 사용자에 대해 분석 요청이 동시에 여러 번 들어올 경우, 시스템은 **Redis 기반 Distributed Lock** 등을 통해 하나의 분석 작업만 수행해야 합니다.
- **GitHub API 장애**: 데이터 수집 중 GitHub API가 실패하면, Celery 작업은 재시도(Retry)를 수행하거나 우아하게 실패하고 기존 데이터를 유지해야 합니다.

## 요구 사항 *(필수)*

### 기능 요구 사항

- **FR-001**: 시스템은 `GET /card.svg` 엔드포인트를 제공하고 `username` 쿼리 파라미터를 받아야 합니다.
- **FR-002**: 시스템은 응답으로 반드시 `Content-Type: image/svg+xml` 헤더를 포함한 유효한 SVG 데이터를 반환해야 합니다.
- **FR-003**: 시스템은 GitHub의 이미지 프록시 캐싱을 방지하기 위해 `Cache-Control: no-cache, no-store, must-revalidate` 헤더를 설정해야 합니다.
- **FR-004**: 시스템은 요청 시 데이터의 존재 여부와 최신성(1시간 기준)을 판단하여 Stale-While-Revalidate 전략을 수행해야 합니다.
- **FR-005**: 시스템은 "분석 필요" 상태일 때, **Celery Task**를 트리거하여 백그라운드에서 분석을 수행해야 합니다.
- **FR-006**: 비동기 분석 작업은 해당 사용자에 대해 이미 진행 중인 작업이 있을 경우 중복 실행을 방지해야 합니다 (Locking).
- **FR-007**: 분석 작업은 GitHub API를 통해 사용자의 활동 이벤트를 수집하고, 기존 데이터가 있다면 그 이후의 데이터만 증분 수집해야 합니다.
- **FR-008**: 분석 작업은 수집된 이벤트 메시지의 감정을 로컬 HuggingFace 모델(`xlm-roberta-base-finetuned-kor-8-emotions`)로 분석하고, 최근 24시간의 맥락을 Gemini Flash Lite를 통해 페르소나로 도출하여 PostgreSQL에 저장해야 합니다.
- **FR-009**: 시스템은 `username`이 누락되거나 내부 오류 발생 시, 텍스트가 포함된 폴백(Fallback) SVG를 반환해야 합니다.

### 주요 엔티티 *(기능에 데이터가 포함된 경우 포함)*

- **GithubUser**: 분석 대상이 되는 GitHub 사용자 정보 (식별자, 마지막 분석 시각 등).
- **GithubEvent**: GitHub API로부터 수집된 원본 이벤트 데이터 및 개별 감정 분석 결과.
- **AnalysisResult**: LLM을 통해 최종 도출된 페르소나 상태, 요약 코멘트, 분석 완료 시각.

## 성공 기준 *(필수)*

### 측정 가능한 결과

- **SC-001**: "Hit & Fresh" 및 "Hit & Stale" 케이스에서 API 응답 시간은 평균 200ms 이내여야 합니다.
- **SC-002**: 유효한 사용자 ID에 대한 최초 요청(Cold Miss) 시, 100% 확률로 플레이스홀더 SVG가 반환되어야 합니다.
- **SC-003**: 만료된 데이터(Stale) 조회 시, Celery 워커에서 10초 이내에 작업 수신이 확인되어야 합니다.
- **SC-004**: 동일 사용자에 대한 동시 요청이 발생하더라도, 실제 분석 로직(ML/LLM)은 1회만 실행되어야 합니다.
